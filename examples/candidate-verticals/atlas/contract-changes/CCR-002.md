# CCR-002 — One-time XAS-CANON-1 re-stamp of historical snapshot `state_hash` values

**Status:** PROPOSED (Muse → Fable review) · **Date:** 2026-10-07
**Raised during:** ATLAS V0 Milestone 1 (world + replay parity)

## 1. Problem

The handoff (§2) and fixture README (invariant 2) prescribe that the real engine
hash with XAS-CANON-1 canonical JSON, and that "M1 re-stamps hashes once, with a
reason". The committed `state_hash` values were produced by the oracle's
`JSON.stringify({state, metrics})` in JS insertion order, which is **not**
canonical (keys unsorted). A canonical engine therefore cannot reproduce the
committed hashes byte-for-byte.

This is not a content disagreement: the independent runtime reconstructs
`{state, metrics}` deep-equal to the frozen files at all four canonical T
(state, metrics, diagnosis, evidence_refs all match). The sole delta is key
ordering in serialization. Canonicalizing the frozen files' own content yields:

| Snapshot | Committed `state_hash` | XAS-CANON-1 of frozen `{state, metrics}` |
|---|---|---|
| `snapshots/s1_normal.json` | `e43bb95a…090` | `7d7139243bb43c08bb910bb7a641588b685c154b4178c11874d60250b70f71bd` |
| `snapshots/s2_bottleneck_emerging.json` | `ce8385bf…2e` | `765d5cb501eccb71fcf890ecb89773ac207f325954c192c34306018186bb06b6` |
| `snapshots/s3_bottleneck_active.json` | `5ed539b8…029` | `67f66b29b3f98237825b633f095ea1da56b4c4dbdf5e072c80b1b9faf4fefa84` |
| `expected/s4_observed_reference.json` | `9542f78f…48f5` | `8de373a7d10fa05056c3227a81ff9f154a8d74de16ae2a4e94cc0132010cc42e` |

The runtime's independently computed hashes equal the right-hand column exactly,
proving the re-stamp values are fully determined by frozen content (no
implementation judgement involved) and that cross-implementation canonical
hashing works as designed.

## 2. Proposed change

Fable performs the prescribed one-time re-stamp:

1. Change the oracle to hash `sha256(canonicalJson({state, metrics}))` with
   XAS-CANON-1 (sorted keys, no whitespace, shortest round-trip numbers) instead
   of bare `JSON.stringify`.
2. Regenerate the four historical snapshots (`s1_normal`, `s2_bottleneck_emerging`,
   `s3_bottleneck_active`, `s4_observed_reference`) — only their `state_hash`
   fields move; all content is already canonical-invariant.
3. Update `manifest.json` file hashes for those four files.
4. Record the reason in `fixtures/restaurant-v0/CHANGELOG.md` (hash-form migration
   to XAS-CANON-1; no content change).

Out of scope for this CCR: the simulated snapshots (`s4_simulated_intervention`,
`s4b_simulated_baseline`) keep emission-order hashes until the simulation
milestones (M8–M10) re-stamp them the same way.

## 3. Affected fixtures and tests

- 4 snapshot files: `state_hash` field only.
- `manifest.json`: 4 file-hash entries.
- `CHANGELOG.md`: one entry.
- Tests: `test/replay.test.ts` hash assertions flip to PASS once the re-stamp
  lands; the test already asserts the canonical values above.

## 4. Migration impact

- Runtime: none (already canonical).
- Oracle: one-line hash change + regeneration.
- Until approved, the `state_hash` check is reported as FAIL (CCR-002 pending);
  section-level parity (state/metrics/diagnosis/evidence_refs) is PASS and is the
  substantive evidence.

## 5. Alternatives considered

- **Runtime mimics oracle insertion order:** reproduces committed hashes today,
  but disobeys the explicit "real engine must use XAS-CANON-1" requirement and
  bakes JS-specific emission order into the hash contract, defeating
  cross-implementation stability. Rejected.
- **Muse re-stamps unilaterally:** would break `oracle --check` (it regenerates
  emission-order hashes and compares against the manifest); the re-stamp must
  travel with the oracle change, i.e. Fable-side. Rejected.
